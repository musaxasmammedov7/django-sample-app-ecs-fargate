# Полное объяснение для новичка: Docker → ECR → ECS Fargate → RDS

Это подробный «разбор снизу вверх» того, что мы сделали и **почему**. Читайте
по порядку — каждый следующий раздел опирается на предыдущий.

---

## Часть 0. Задача простыми словами

Был сайт на Django. Чтобы он работал, нужны три вещи:

1. **Код приложения** (Django).
2. **Среда для запуска** (Python, библиотеки, веб-сервер).
3. **База данных** (PostgreSQL).

Раньше всё это настраивали на EC2 — обычном «виртуальном компьютере» в AWS.
Проблема: серверы ломаются, их надо патчить, обновлять, и если сервер упал — сайт
лёг. В задаче просят перейти на **контейнеры** и **ECS Fargate**: тогда AWS сам
заботится о «железе», а мы описываем только *что* запускать, а не *на каком
компьютере*.

## Часть 1. Контейнеры и Docker

### 1.1. Что такое контейнер

**Контейнер** — это упакованное приложение вместе со всем, что ему нужно:
код, библиотеки, настройки. Он работает одинаково на ноутбуке и в AWS, потому что
внутри контейнера своя мини-ОС (обычно Linux).

Аналогия: контейнер — это как **посылка**, в которой лежит всё необходимое.
Куда посылку ни привези, содержимое не меняется.

**Важно различать:**

| Понятие | Что это |
|---|---|
| **Образ (image)** | «Чертёж»/шаблон, из которого делают контейнеры. Только для чтения. |
| **Контейнер** | Запущенный экземпляр образа. Из образа можно запустить 1, 10, 100 контейнеров. |
| **Слой (layer)** | Образ состоит из слоёв. Каждая инструкция в Dockerfile добавляет слой. Слои кэшируются и переиспользуются. |
| **Реестр (registry)** | Хранилище образов. У нас — **Amazon ECR**. Пример публичного — Docker Hub. |

### 1.2. Почему Docker, а не «просто скопировать файлы на сервер»

Без Docker: «у меня работает, у тебя нет» — разные версии Python, библиотек,
системных пакетов. С Docker: образ один и тот же везде. Плюс контейнеры быстро
запускаются и легко масштабируются.

### 1.3. Наш `Dockerfile` — построчно

Dockerfile — это инструкция, как собрать образ. У нас он **multi-stage**
(многоэтапный): есть этап «builder» (где мы собираем) и «runtime» (что реально
попадёт в прод).

**Этап 1 — builder:**

```dockerfile
FROM python:3.12-slim-bookworm AS builder
```
Берём официальный образ Python 3.12 (приложению нужно ≥3.12).

```dockerfile
RUN apt-get install ... build-essential pkg-config libpq-dev libcurl4-openssl-dev ...
```
Ставим **инструменты сборки**. Они нужны, потому что часть Python-библиотек
(`psycopg`, `pycurl`, `cryptography`) компилируются из C-кода. `libpq-dev` — для
PostgreSQL, `libcurl`/`libssl` — для `pycurl`.

```dockerfile
RUN python -m venv /opt/venv
RUN pip install -r requirements.txt -r requirements-prod.txt
```
Создаём «изолированную папку» с Python-библиотеками (venv) и ставим зависимости.
`requirements-prod.txt` — это `gunicorn`, которого нет в основном
`requirements.txt`.

**Этап 2 — runtime:**

```dockerfile
FROM python:3.12-slim-bookworm AS runtime
RUN apt-get install ... libpq5 libcurl4 tzdata
COPY --from=builder /opt/venv /opt/venv
```
Второй, **чистый** образ. Мы ставим только то, что нужно *во время работы*
(`libpq5`, `libcurl4`), и копируем готовый venv из builder. Компиляторы
(`build-essential` и прочее) в прод **не попадают** — образ меньше и безопаснее.

```dockerfile
RUN groupadd ... app && useradd ... app
USER 1000:1000
```
Создаём непривилегированного пользователя и запускаем контейнер от него. Если
приложение взломают, атакующий получит мало прав. Это best practice.

```dockerfile
RUN SECRET_KEY=build-time-placeholder python manage.py collectstatic --noinput \
 && SECRET_KEY=build-time-placeholder python manage.py compress --force
```
Django-статика (CSS/JS) собирается **во время сборки образа**. `SECRET_KEY`
здесь — временная заглушка только чтобы Django «проснулся». Настоящий секрет
подставится при запуске (см. Часть 8).

```dockerfile
ENTRYPOINT ["/app/docker/entrypoint.sh"]
CMD ["gunicorn", "hc.wsgi:application", "--bind", "0.0.0.0:8000", ...]
```
`ENTRYPOINT` — что запускать при старте контейнера; `CMD` — аргументы. Gunicorn —
это **прод-веб-сервер** для Django (`manage.py runserver` только для разработки!).

### 1.4. `entrypoint.sh` — что происходит при старте

```bash
wait-for-DB  ->  python manage.py migrate  ->  exec gunicorn
```

1. **Ждём базу**: RDS только что создан и может отвечать не сразу. Скрипт
   «стучится» в порт 5432, пока не откроется.
2. **Миграции**: `migrate` создаёт/обновляет таблицы в БД.
3. **`exec gunicorn`**: `exec` заменяет процесс shell на gunicorn — важно, чтобы
   именно gunicorn получал сигналы остановки от ECS.

## Часть 2. Amazon ECR — хранилище образов

**ECR** (Elastic Container Registry) — это «Docker Hub» внутри вашего AWS-аккаунта.
Туда CI/CD (или вы вручную) загружает (push) образ. ECS оттуда его скачивает
(pull).

Что мы настроили в `ecs.tf`:

- **`aws_ecr_repository`** — сам репозиторий `django-sample-app`.
- **`scan_on_push`** — ECR автоматически сканирует образ на известные уязвимости
  при загрузке.
- **Шифрование** `AES256`.
- **Lifecycle policy** — автоматически удаляет старые/неподписанные образы,
  чтобы не платить за хлам.

Адрес образа выглядит так:
`123456789012.dkr.ecr.eu-north-1.amazonaws.com/django-sample-app:abc1234`
(`<аккаунт>.dkr.ecr.<регион>.amazonaws.com/<имя>:<тег>`).

## Часть 3. ECS: кластер, задача, сервис (важнейшая часть)

**ECS** (Elastic Container Service) — это «оркестратор»: система, которая решает,
*где* и *сколько* контейнеров запускать, следит за их здоровьем и
перезапускает упавшие.

Три главных понятия:

### 3.1. Кластер (Cluster)
Логическая группа, «рабочая область» для наших контейнеров. Не сервер, а просто
группа. Мы назвали его `django-sample-app`.

### 3.2. Task Definition (определение задачи)
Это «паспорт» контейнера: **что запускать**. Внутри:

- **образ** (из ECR),
- **сколько CPU и памяти** выделить,
- **порты** (у нас 8000),
- **переменные окружения** (`DB_HOST`, `DEBUG` и т.д.),
- **секреты** (`SECRET_KEY`, `DB_PASSWORD` — из Secrets Manager),
- **роли IAM** (какие права у контейнера),
- **куда писать логи** (CloudWatch).

Думайте о Task Definition как о «реестре параметров одного запуска приложения».

### 3.3. Service (сервис)
Сервис следит, чтобы **всегда работало нужное число** копий задачи
(`desired_count`). Если задача упала — сервис поднимет новую. Если выходит новая
версия — сервис делает **rolling update** (по одной заменяет старые задачи
новыми, без простоя).

У нас: `desired_count = 1`, но задан `deployment_minimum_healthy_percent = 100`
и `maximum = 200` — при обновлении ECS сначала поднимет новую задачу, дождётся,
что она здорова, и только потом убьёт старую.

### 3.4. Сколько копий? Зачем `desired_count`
Можно поставить 2+ — тогда при падении одной копии сайт продолжит работать.
Для учебного стенда достаточно 1 (дешевле). Для прода — минимум 2 в разных AZ.

## Часть 4. Fargate vs EC2 — то, что вы не поняли

Это **два способа**, как ECS запускает контейнеры.

### 4.1. ECS на EC2 (старый способ)
Вы сами создаёте EC2-серверы (виртуальные машины) и говорите ECS: «запускай мои
контейнеры вот на этих серверах». Вы отвечаете за:

- обновление и патчинг ОС,
- выбор типа инстанса,
- масштабирование серверов,
- оплату за сервер 24/7, даже если контейнер ничего не делает.

Плюс: дешевле при большой постоянной нагрузке, полный контроль.

### 4.2. ECS на Fargate (наш выбор)
**Fargate — это «серверлес» режим.** Вы вообще не создаёте EC2. Вы говорите
только: «хочу X CPU и Y памяти для задачи». AWS сам находит/создаёт под это
вычислительные ресурсы, запускает контейнер и берёт с вас деньги **за время
работы задач**.

Вы отвечаете **только** за образ и параметры. Никаких серверов, патчей, ASG.

Плюс: минимум обслуживания, быстро стартовать.
Минус: дороже на единицу ресурсов при большой стабильной нагрузке.

### 4.3. Как это выглядит в коде

```hcl
launch_type              = "FARGATE"
requires_compatibilities = ["FARGATE"]
cpu                      = 512     # 0.5 vCPU
memory                   = 1024    # 1 ГБ
network_mode             = "awsvpc"  # у каждой задачи свой IP и свой ENI
```

`network_mode = "awsvpc"` — каждая задача получает **собственный сетевой
интерфейс и приватный IP** в вашей VPC. Поэтому target group ALB имеет
`target_type = "ip"` (регистрируем именно IP задачи).

### 4.4. Ещё про Fargate CPU/RAM
Допустимые комбинации фиксированы (например, 512 CPU = 256…4096 МБ). Мы взяли
512/1024. Архитектура — `X86_64` (есть ещё `ARM64`/Graviton, дешевле на ~20%,
но образ нужно собирать под arm64).

## Часть 5. Сеть: VPC, сабнеты, ALB

### 5.1. VPC
**VPC** (Virtual Private Cloud) — это ваша изолированная «сеть» в AWS со своими
диапазонами IP. У нас `10.0.0.0/16`.

### 5.2. Availability Zone и сабнеты
AWS состоит из **AZ** — физически разных дата-центров. Чтобы пережить отказ
одного ДЦ, ресурсы разносят по 2–3 AZ.

Внутри VPC делают **сабнеты** (подсети):

- **Публичные** — есть доступ в интернет. Там живёт **ALB** и **NAT Gateway**.
- **Приватные** — без прямого доступа из интернета. Там живут **ECS-задачи** и
  **RDS**. Это безопасно: база и приложение не видны из интернета.

Как приватные всё же скачивают образ и пишут логи? Через **NAT Gateway**:
трафик «наружу» идёт, а «внутрь» — нет.

### 5.3. Security Groups (SG) — «брандмауэры»
Правила, кто к кому может подключаться. У нас три:

- **ALB SG**: принимает 80/443 из интернета (`0.0.0.0/0`).
- **ECS SG**: принимает порт 8000 **только от ALB SG**.
- **RDS SG**: принимает 5432 **только от ECS SG**.

Это принцип минимальных привилегий: база доступна только приложению, а
приложение — только балансировщику. Прямо из интернета до них не достучаться.

### 5.4. ALB (Application Load Balancer)
**ALB** — точка входа. Он:

1. принимает HTTP из интернета,
2. проверяет здоровье задач (**health check**, у нас `/api/v3/status/`),
3. распределяет трафик между задачами,
4. шлёт трафик только в «здоровые» задачи.

Связка: у ALB есть **listener** (слушает порт 80) и **target group** (список
задач, куда перенаправлять). Каждая запущенная задача автоматически
регистрируется в target group по своему IP.

### 5.5. Что такое AZ в нашем коде
```hcl
azs             = slice(data.aws_availability_zones.available.names, 0, var.availability_zone_count)
private_subnets = [...]
public_subnets  = [...]
```
Мы спрашиваем у AWS список доступных зон и берём первые 2. Сабнеты режут диапазон
`10.0.0.0/16` на куски через `cidrsubnet`.

## Часть 6. RDS PostgreSQL — база данных

### 6.1. Почему managed, а не PostgreSQL в контейнере
Можно поднять БД контейнером рядом, но данные надо где-то хранить, делать
бэкапы, обновлять, обеспечивать отказоустойчивость. **RDS** делает это за вас:
автобэкапы, патчи, снапшоты, Multi-AZ.

### 6.2. Что настроено

```hcl
engine                 = "postgres"
instance_class         = "db.t4g.micro"   # маленький, для учёбы
allocated_storage      = 20
storage_encrypted      = true             # шифрование диска
multi_az               = false            # для прода -> true
backup_retention_period = 7               # авто-бэкапы 7 дней
manage_master_user_password = true        # пароль в Secrets Manager
```

### 6.3. Как приложение подключается к БД
Приложение читает переменные окружения (`hc/settings.py`):

```env
DB=postgres
DB_HOST=<адрес RDS>
DB_PORT=5432
DB_NAME=hc
DB_USER=hc
DB_PASSWORD=<из Secrets Manager>
DB_SSLMODE=require
```

`DB_SSLMODE=require` — соединение обязательно по TLS.

### 6.4. Пароль базы — где он
`manage_master_user_password = true` означает: AWS сам сгенерирует пароль
мастера и будет хранить его в **AWS Secrets Manager**. Пароль **не попадает** в
Terraform-код и state. ECS при запуске задачи читает секрет через специальный
механизм `secrets` и подставляет в переменную `DB_PASSWORD`.

## Часть 7. IAM и роли (кто что имеет право делать)

**IAM** — система прав в AWS. Есть несколько ролей, каждая — со своими правами.

- **Task Execution Role** — «сервисная» роль ECS. Нужна, чтобы:
  - скачать образ из ECR,
  - писать логи в CloudWatch,
  - прочитать секреты из Secrets Manager.

  Мы даём ей доступ **только** к нашим двум секретам через
  `task_exec_secret_arns` (принцип наименьших привилегий).

- **Task Role** — роль самого приложения (если приложению нужен доступ к
  другим AWS-сервисам, например S3). У нас приложению AWS-доступ не нужен.

- **GitHub Actions Role (OIDC)** — роль для CI/CD. GitHub Actions
  аутентифицируется в AWS **без паролей и ключей**, по протоколу **OIDC**
  (GitHub «предъявляет» подписанный токен, AWS его проверяет и выдаёт временный
  доступ). В trust policy прописано: только репозиторий `owner/name` и только
  ветка `main`. Если токен украдут, он всё равно короткоживущий и привязан к
  репозиторию.

## Часть 8. Секреты: Secrets Manager

**Никогда** нельзя хранить пароли в коде/git. Поэтому:

- пароль RDS генерит AWS и кладёт в Secrets Manager;
- `SECRET_KEY` Django генерит Terraform (`random_password`) и кладёт туда же;
- в Task Definition указывается **ссылка** на секрет, а не значение:

```hcl
secrets = [
  { name = "SECRET_KEY", valueFrom = "<arn>:SECRET_KEY::" },
  { name = "DB_PASSWORD", valueFrom = "<arn>:password::" },
]
```

Ключ после ARN (`:SECRET_KEY::`) означает нужное поле в JSON-секрете. ECS сам
подставит значение в переменную окружения при старте контейнера — в описании
задачи и в логах видны только ссылки.

## Часть 9. Terraform — инфраструктура как код

### 9.1. Зачем
Вместо «пощёлкать в консоли AWS» вы описываете ресурсы в `.tf`-файлах. Плюсы:
воспроизводимость, ревью в git, откат, автоматизация.

### 9.2. Основной цикл
```bash
terraform init      # скачать провайдеры/модули
terraform plan      # показать, ЧТО будет создано/изменено/удалено
terraform apply     # применить
terraform destroy   # удалить всё
```

- **Provider** — плагин для общения с API (у нас `hashicorp/aws`).
- **State** — файл, где Terraform помнит, что уже создано. В реальном проекте
  хранится в S3 (remote state), а не локально.
- **Variables** — входные параметры (`variables.tf`).
- **Outputs** — результат (`outputs.tf`), например `application_url`.
- **Модули** — переиспользуемые куски конфигурации.

### 9.3. Почему мы берём готовые модули
Писать VPC/ALB/RDS/ECS «с нуля» — сотни строк и легко ошибиться. Модули
**terraform-aws-modules** (автор Anton Babenko) — проверенные сообществом,
обновляемые, с правильными настройками по умолчанию. Это индустриальный
стандарт. Наш код — это в основном «склейка» этих модулей с нашими значениями.

### 9.4. Наш порядок применения (bootstrap)
1. `terraform apply` создаёт ECR, VPC, RDS, ALB, IAM и **пустой** ECS-сервис.
   Образы в ECR ещё нет, поэтому задачи не поднимутся — это нормально.
2. CI/CD собирает образ, пушит в ECR.
3. CI регистрирует новую ревизию Task Definition с этим образом и обновляет
   сервис — задачи поднимаются и становятся здоровыми.

Поэтому в `ecs.tf` стоит `ignore_task_definition_changes = true`: чтобы
Terraform потом не «откатил» образ, который задеплоил пайплайн.

## Часть 10. CI/CD, Trivy и dive

### 10.1. CI/CD
**CI** — непрерывная интеграция (собираем и тестируем на каждый push).
**CD** — непрерывная доставка (автоматически деплоим).

Наш `.github/workflows/ci-cd.yml` при push в `main`:

1. `manage.py check` + проверка, что нет незакоммиченных миграций;
2. **hadolint** проверяет Dockerfile;
3. **Trivy** сканирует исходники и IaC (уязвимости, секреты, ошибки конфигов);
4. **Syft** строит SBOM, **Grype** (Anchore) сканирует зависимости;
5. собирает образ (`linux/amd64`);
6. **Trivy** и **Grype** сканируют образ; при HIGH/CRITICAL — **падает**, деплоя не будет;
7. пушит в ECR;
8. регистрирует новую ревизию задачи и обновляет ECS-сервис;
9. ждёт, пока сервис выйдет в стабильное состояние.

Terraform (IaC) проверяется **отдельным** workflow
`.github/workflows/terraform.yml` (`fmt` + `validate`).

### 10.2. Trivy
Инструмент сканирования. Смотриr:

- **vuln** — известные CVE в пакетах/ОС образа;
- **secret** — случайно «зашитые» пароли/ключи в коде/образе;
- **misconfig** — ошибки конфигурации IaC/Docker.

Результаты отправляются в **GitHub Security** (вкладка Security → Code scanning)
в формате SARIF, чтобы их было удобно смотреть.

### 10.3. dive
Локальный инструмент для **анализа слоёв образа**:

```bash
brew install dive
dive django-sample-app:local
```

Показывает, сколько весит каждый слой, какие файлы дублируются, и выдаёт
«Health score». Цель — маленький эффективный образ без мусора. Именно поэтому у
нас multi-stage и `.dockerignore`.

## Часть 11. Как всё связано: путь одного запроса

```
Пользователь открывает http://<alb-dns>/
   │
   ▼
ALB (публичный сабнет) — слушает :80
   │  проверяет health check /api/v3/status/
   ▼
target group (target_type=ip)
   │
   ▼
ECS Fargate task (приватный сабнет, IP задачи) :8000
   │  gunicorn → Django
   ▼
RDS PostgreSQL (приватный сабнет) :5432
   │  пароль из Secrets Manager
   ▼
```

## Часть 13. Частые вопросы новичка

**Это будет стоить денег?**
Да. Платно: NAT Gateway (почасово), ALB, Fargate-задачи, RDS, Secrets Manager,
ECR. Для учебного стенда недорого, но не забывайте `terraform destroy` после
проверки. Если не удалить — будет «капать» каждый час.

**Почему задачи ECS в PENDING?**
Чаще всего образа ещё нет в ECR (не запушили) либо нет выхода в интернет через
NAT (не может скачать образ).

**Почему ALB target unhealthy?**
Приложение не стартовало: ошибка миграций или подключения к БД. Смотрите логи в
CloudWatch (`aws logs tail /aws/ecs/... --follow`).

**Можно ли сделать HTTPS?**
Да. Нужен домен + сертификат в ACM. В `alb.tf` в комментарии показано, как
добавить listener на 443 и редирект с 80.

**Fargate vs EKS — что выбрать?**
EKS — это Kubernetes (мощнее, но сложнее). Для простого приложения ECS Fargate
проще и дешевле в сопровождении. ECS — рекомендованный старт.
