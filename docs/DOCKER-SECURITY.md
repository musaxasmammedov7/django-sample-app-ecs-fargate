## 1. Что меняем в Dockerfile и почему

Все изменения привязаны к **CIS Docker Benchmark** и **OWASP Docker Top 10** —
это признанные чек-листы безопасности контейнеров.

### 1.1. Базовый образ закреплён по digest (supply-chain)
Было: `FROM python:3.12-slim-bookworm` — тег можно перетегировать, и в один
прекрасный день вы соберёте «не то» (атака на цепочку поставок).
Стало: `...@sha256:9901e0a8...` — неизменяемый отпечаток. Теперь мы точно знаем,
*какой именно* образ используется. Обновление — осознанное действие.

### 1.2. Multi-stage сборка (уже была, оставили)
Компиляторы (`gcc`, `build-essential`) и dev-библиотеки остаются в `builder` и
**не попадают** в прод. Меньше файлов → меньше потенциальных уязвимостей и
меньше размер образа.

### 1.3. Минимум пакетов в runtime
Ставим только `libpq5`, `libcurl4`, `ca-certificates`, `tzdata`. Нет `bash`
(есть sh), нет `curl`, нет `ssh`, нет менеджера пакетов в рабочем слое — меньше
инструментов у атакующего. `apt`-листы и pip-кэш удаляем.

### 1.4. Запуск от непривилегированного пользователя
`USER 1000:1000`. Если злоумышленник получит выполнение кода внутри контейнера,
он будет не root и не сможет, например, ставить пакеты или менять
системные файлы. Это самый важный практический запрет.

### 1.5. Убираем setuid/setgid и права на запись
```
find / -xdev -type f -perm /6000 -exec chmod a-s {} +
chmod -R go-w /app
```
setuid-бинарники — классический путь повышения привилегий. Мы их обнуляем; а
`/app` делаем недоступным на запись для группы и остальных.

### 1.6. Секреты не «запекаются» в образ
`SECRET_KEY` и `DB_PASSWORD` **не** пишутся в слои. На сборке используется
временный ключ-заглушка только чтобы Django собрал статику, а реальные значения
ECS подставляет в рантайме из AWS Secrets Manager. Проверить, что секрета нет в
образе, можно так: `docker history --no-trunc <image>`.

### 1.7. Проверка здоровья и STOPSIGNAL
- **Проверка здоровья делается средствами ECS, а не Docker.** Инструкция
  `HEALTHCHECK` в Dockerfile сознательно **не используется**: ECS Fargate её
  игнорирует (она влияет только на локальный `docker run`). Вместо неё:
  - `healthCheck` в описании контейнера (task definition, `ecs.tf`) — ECS сам
    опрашивает `/api/v3/status/` внутри контейнера;
  - health check на target group в **ALB** (`alb.tf`) — определяет, слать ли
    трафик в задачу.
- `STOPSIGNAL SIGTERM` — при остановке gunicorn корректно завершает запросы
  (graceful shutdown), а не обрывает их.

### 1.8. Runtime-закалка (Docker / ECS)
При запуске контейнера применяются:
```yaml
user: "1000:1000"
read_only: true                          # корневая ФС только для чтения
tmpfs: ["/tmp:size=64m"]                 # единственная записываемая папка
cap_drop: [ALL]                          # отбираем ВСЕ Linux capabilities
security_opt: [no-new-privileges:true]   # запрет повышения привилегий
init: true                               # PID 1, переработка зомби-процессов
```
В ECS для Fargate включён `initProcessEnabled = true`. `readonlyRootFilesystem`
оставлен `false`, потому что Fargate не даёт смонтировать tmpfs для `/tmp`; при
запуске через `docker run` рекомендован read-only корень с `--tmpfs /tmp`.

## 3. Инструменты сканирования

### 3.1. Trivy (Aqua Security) — основной
Ищет:
- **vuln** — CVE в пакетах ОС и языка;
- **secret** — токены/пароли, случайно попавшие в код;
- **misconfig** — ошибки в Dockerfile и Terraform.

```bash
trivy config Dockerfile              # misconfig самого Dockerfile
trivy fs .                           # зависимости + секреты + IaC
trivy image django-sample-app:local  # уязвимости готового образа
```

### 3.2. Anchore: Syft + Grype — «второе мнение» и SBOM
- **Syft** строит **SBOM** (Software Bill of Materials) — полный список того,
  что внутри образа/проекта. Нужен для аудита и контроля цепочки поставок.
  ```bash
  syft dir:. -o spdx-json=sbom.spdx.json
  ```
- **Grype** сканирует SBOM или образ на уязвимости.
  ```bash
  grype sbom:sbom.spdx.json
  grype docker:django-sample-app:local
  ```

### 3.3. Clair (CoreOS/Quay)
Серверный сканер, обычно встроен в реестр (Quay/Clair). Идея та же: сверяет
слои образа с базой CVE. Для локальной проверки чаще берут Trivy/Grype, а Clair
используют как сервис в CI/реестре.

### 3.4. Docker Scout
Встроенный в Docker Desktop/CLI сканер: `docker scout cves <image>`. Удобен для
быстрой проверки локально, использует свою базу.

### 3.5. hadolint
Линтер Dockerfile: ловит опечатки и антипаттерны (незакреплённые пакеты,
`latest`, лишний root и т.п.). У нас — 0 замечаний.

### 3.6. Как это встроено в CI
`.github/workflows/ci-cd.yml` на каждый push и раз в неделю запускает
hadolint, Trivy (IaC), Syft (SBOM) и Grype (зависимости + образ). Результаты
уходят во вкладку **Security** в GitHub (SARIF), а SBOM сохраняется артефактом.

## 5. Task 4*: Другие виды контейнеров — Kata и LXC

«Контейнер» — не одна технология, а несколько, с разным уровнем изоляции.

### 5.1. runc (то, что использует Docker по умолчанию)
Контейнер = **namespaces** (изоляция видимости) + **cgroups** (лимиты ресурсов),
разделяющие **общее ядро** хоста. Быстро и легко, но если в ядре есть
уязвимость (для побега из контейнера), она общая для всех.

### 5.2. Kata Containers
Kata запускает контейнер внутри **лёгкой виртуальной машины** с собственным
ядром. То есть это «контейнер по интерфейсу, ВМ по изоляции». Даёт гораздо
более сильную границу безопасности (гость не делит ядро с хостом), ценой чуть
большего оверхеда запуска и памяти. Для мультитенантных сред с недоверенным
кодом это правильный выбор.

### 5.3. LXC / LXD
Это «системные контейнеры»: внутри работает полноценный Linux-дистрибутив с
инициализацией, как в лёгкой ВМ, но на общем ядре. Очень удобны для запуска
«машины как процесса» (systemd, несколько сервисов), больше похожи на chroot +
namespaces, чем на однопроцессный Docker-контейнер.

### 5.4. Можно ли применить Kata в нашем стеке (ECS Fargate)?
Короткий ответ: **нет, на ECS Fargate Kata напрямую не включается.** Причины:

- Fargate — **управляемый** сервис: мы не выбираем container runtime, там
  всегда runc-совместимый runtime, и параметра «запусти через Kata» нет.
- ECS на EC2 (launch type = EC2) тоже рассчитан на runc через ECS-агент;
  механизма `RuntimeClass`, как в Kubernetes, в ECS нет.

**Но нужный уровень изоляции у нас уже есть:** под капотом Fargate запускает
каждую задачу в **Firecracker microVM** — это та же идея, что у Kata:
отдельная лёгкая виртуальная машина со своим ядром. То есть «Kata-подобная»
изоляция на Fargate доступна «бесплатно» и по умолчанию.

### 5.5. Как реализовать Kata «по-настоящему»
Kata требует **Kubernetes (EKS)** или ручного containerd — это отдельная
инфраструктура, а не опция ECS.

**Вариант A — EKS + RuntimeClass:**
```yaml
# 1) Класс рантайма
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: kata
handler: kata
```
```yaml
# 2) В pod/деплойменте указываем класс
spec:
  runtimeClassName: kata
  containers:
    - name: app
      image: <ecr>/django-sample-app:<tag>
```

**Вариант B — standalone containerd на Linux:**
1. установить `kata-containers`;
2. прописать рантайм в `/etc/containerd/config.toml`:
   ```toml
   [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.kata]
     runtime_type = "io.containerd.kata.v2"
   ```
3. перезапустить containerd и запускать:
   ```bash
   nerdctl run --runtime io.containerd.kata.v2 -it alpine sh
   ```

**Важно:** на macOS (Docker Desktop) Kata не поддерживается — нужен Linux-хост
или managed-сервис с поддержкой RuntimeClass.

### 5.6. Сравнение

| Технология | Изоляция | Ядро | Скорость старта | Когда выбирать |
|---|---|---|---|---|
| **runc/containerd** (Docker) | средняя | общее | мс | обычные приложения, доверенный код |
| **Kata Containers** | высокая (микро-ВМ) | своё | сотни мс | недоверенный/мультитенантный код |
| **Firecracker** (под Fargate) | высокая (микро-ВМ) | своё | сотни мс | то же, что Kata, но уже встроено в ECS Fargate |
| **LXC/LXD** | средняя-высокая | общее | секунды | «системные» контейнеры, несколько сервисов |

### 5.7. Вывод для клиента
Наше приложение (один процесс gunicorn, доверенный код, Fargate) уже работает
в микро-ВМ Firecracker, поэтому отдельный Kata не нужен — это была бы лишняя
инфраструктура (EKS). Kata стоит рассмотреть, только если появится требование
запускать **недоверенный пользовательский код** и при этом использовать EKS.

## 6. Что осталось «принятым риском» (и почему)

Trivy по IaC показал два замечания по ALB — мы их осознанно принимаем и
документируем:

- **[HIGH] AWS-0053 — ALB смотрит в интернет.** Так и задумано: это публичный
  веб-сайт. Внутренний ALB сделал бы сайт недоступным.
- **[CRITICAL] AWS-0054 — ALB слушает HTTP без TLS.** Закрывается добавлением
  домена + сертификата ACM: в `alb.tf` есть готовый закомментированный блок
  (listener 443 + редирект с 80). Пока домена нет, включать HTTPS нечестно —
  сертификат не выпустить.

Остальные срабатывания Trivy — внутри загруженных модулей (rds, security-group)
и не зависят от нашего кода.
